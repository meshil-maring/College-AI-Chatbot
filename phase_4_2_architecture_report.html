Phase 4.2 — Conversation Record Investigation Report

Complete architectural, relational database, transaction boundary, and persistence flow mapping for the College AI Chatbot platform.

Section A • Existing Relational Database Schema Inspection

Authoritative review of schemaV2_export.sql and Supabase DDL definitions for conversational and generation records.

1. conversations

Primary Container for multi-turn sessions.

  • conversation_id: UUID (PK, default gen_random_uuid())
  • user_id: UUID (FK → users.id)
  • title: TEXT (nullable)
  • status: TEXT ('active' | 'archived')
  • created_at / updated_at: TIMESTAMPTZ
2. messages

Sequential Dialogue Turns in conversation.

  • message_id: UUID (PK)
  • conversation_id: UUID (FK → conversations)
  • message_sequence: INT (1-based, > 0)
  • message_type: 'user' | 'assistant'
  • content_text: TEXT (length > 0)
  • Constraint: UNIQUE(conversation_id, message_sequence)
3. ai_responses

Technical LLM Telemetry (1:1 with assistant message).

  • ai_response_id: UUID (PK)
  • message_id: UUID (FK → messages.message_id, UNIQUE)
  • provider_name: TEXT
  • model_name: TEXT
  • validation_status: 'pending' | 'passed' | 'failed'
  • input_token_count / output_token_count: INT
  • latency_ms: INT

Sections B & C • Approved Schema Source & Backend Models

Approved Schema Source

The single authoritative schema source for the College AI Chatbot is schemaV2_export.sql in the repository root. All table names (conversations, messages, ai_responses) and column constraints conform to PostgreSQL standard DDL.

Current Backend Models (Phase 4.1 State)

Currently, backend/app/schemas/chat.py and session.py handle request-scoped volatile contexts (session_id). Phase 4.2 requires creating domain schemas for ConversationCreate, MessageCreate, and AIResponseCreate.

Section D • Request Execution Flow & Persistence Insertion Point

Safest Insertion Point: Persistence must occur post-generation in process_chat_request() (or dedicated orchestrator), after OpenRouter generation completes successfully and token/latency metrics are known. 
1. POST /api/v1/generation/chat (FastAPI Route)
   ├── Auth Extraction: get_current_user (User ID extracted from Supabase JWT)
   ├── Session/Conversation Resolution:
   │   └── Find or Create conversation row in DB (status='active', user_id)
   ├── Persistence (Turn 1 - User Message):
   │   └── INSERT INTO messages (conversation_id, message_sequence=N, message_type='user', content_text)
   ├── Phase 3 Retrieval (if chunks not pre-supplied):
   │   └── retrieve(RetrievalRequest) -> Vector Search & Chunk Mapping
   ├── Phase 4 Generation:
   │   └── assemble_context() -> AIGenerationService.generate() (OpenRouter / gpt-4o-mini)
   ├── Persistence (Turn 2 - Assistant Message & AI Response):
   │   ├── INSERT INTO messages (conversation_id, message_sequence=N+1, message_type='assistant', content_text)
   │   └── INSERT INTO ai_responses (message_id, provider_name, model_name, token_counts, latency_ms)
   └── Return ChatResponse (including conversation_id, message_id, session_id)

Sections E, F, G • Semantic Model & Invariants

Conversation Semantics
  • conversation_id is the persistent database identity.
  • session_id (Phase 4.1) maps 1:1 to conversation_id.
  • Auto-title generation from initial user query (e.g. truncated first 60 chars).
  • Conversations belong strictly to authenticated user_id.
Message Semantics
  • Strict sequence monotonicity: message_sequence starts at 1 and increments by 1.
  • Constraint: UNIQUE(conversation_id, message_sequence) prevents turn overlap.
  • Strict type enum: 'user' | 'assistant'.
AI Response Semantics
  • 1:1 relationship with assistant message (unique message_id FK).
  • Captures true OpenRouter execution metadata.
  • validation_status = 'passed' when grounded/honest.
  • Non-negative latency and token counts.

Sections H & I • Phase 4.2 vs Phase 4.3 Boundaries & Transactions

Phase 4.2 MUST IMPLEMENT:
  • conversations record creation / lookup.
  • messages record insertion (both user and assistant turns).
  • ai_responses record insertion (generation metrics and status).
  • Atomic transaction support via repository/service layer.
Phase 4.2 MUST NOT IMPLEMENT (Phase 4.3 Scope):
  • message_citations insertion or chunk citation mapping.
  • retrieval_operations persistence.
  • Modifications to Phase 3 vector search, chunking, or ingestion pipelines.
  • Changes to OpenRouter model parameters or prompt templates.

Sections J, K, L • Security, Auth, & API Contract

Security & RLS

Authenticated Context: FastAPI route utilizes get_current_user to extract validated user_id from the Supabase JWT. Repository layer uses get_admin_client() for server-side persistence while enforcing user_id ownership guards at the application layer.

API Contract Evolution

Seamless Compatibility: ChatRequest accepts optional conversation_id (or aliases session_id). ChatResponse returns conversation_id, message_id, and session_id to guarantee zero breakage for Phase 4.1 consumers.
