## 1. Objective

A secure student notification and academic-alert foundation. Students receive relevant academic notifications generated from authoritative college data (attendance alerts, published test/exam results, academic result publication, academic status changes, and student-specific administrative notifications).

**The notification system is NOT a second source of truth.** Every notification references authoritative records already owned by the institution/student data model via `source_record_id` + `source_type`. Notifications are generated by explicit service/repository functions invoked by authorized backend workflows — never by students, and never from client-supplied identity.

Security invariant enforced:

```
Authenticated JWT
    -> canonical student context (Phase 6.9 student_context.get_student_context)
    -> student_id + institution_id (server-derived)
    -> own-notification scoped reads / read-state mutations
```

Never: `client-supplied student_id / user_id / institution_id / auth_user_id -> ownership`.

## 2. Scope delivered

- **A. Student notification listing** — `GET /api/v1/students/me/notifications`
  - authenticated student only; own notifications only; deterministic ordering (`created_at DESC`); pagination (`page` / `page_size`, max 100); unread/read state (`is_read`, `read_at`); `created_at`; notification type/category; title/message; optional reference to the authoritative source record.
- **B. Notification read state** — `PATCH /api/v1/students/me/notifications/{notification_id}/read`
  - Students can mark their OWN notification read. They CANNOT modify another student's notification, modify ownership, change `institution_id`, alter type/content, or create arbitrary notifications. The read endpoint accepts no payload.
- **C. Notification categories** — controlled vocabulary:
  - `attendance_alert`, `result_published`, `academic_status`, `academic_admin`
  - Enforced at the schema (regex + closed set), service (`_validate_notification_type`), and database (CHECK constraint) layers. No unnecessary categories were added.
- **D. Academic alerts foundation** — `app/services/student_notifications_integration.py` provides explicit, opt-in service functions for authorized backend workflows:
  - `notify_attendance_alert` (source_type `attendance_record`)
  - `notify_result_published` (source_type `student_result`)
  - `notify_test_result_published` (source_type `test_result`)
  - `notify_academic_status` (source_type `academic_status`)
  - `notify_academic_admin` (source_type `academic_admin`)
  - No external event infrastructure was invented. These are service hooks a later attendance/result workflow MAY call.

## 3. API surface

Registered under the existing `/api/v1` prefix with the existing `get_current_user` dependency and Phase 6.9 student-context tenant enforcement:

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/v1/students/me/notifications` | Paginated own-notification listing |
| GET | `/api/v1/students/me/notifications/{notification_id}` | One own notification |
| GET | `/api/v1/students/me/notifications/unread-count` | Unread count for the authenticated student |
| PATCH | `/api/v1/students/me/notifications/{notification_id}/read` | Mark own notification read |

No endpoint accepts a `student_id`, `user_id`, `institution_id`, or notification content payload. Students have no API to create notifications.

## 4. Security posture

- **Identity resolution:** every endpoint resolves the student context via `student_context.get_student_context(current_user)` (Phase 6.9 canonical chain). Eligibility (approved + active + institution active) is enforced by the locked Phase 6.9 resolver — a non-student / unapproved / inactive account cannot reach the notification service.
- **Ownership:** `get_own_notification` / `mark_own_notification_read` return the SAME `404 NOTIFICATION_NOT_FOUND` when a notification is missing OR belongs to another student (no enumeration).
- **Tenant:** `institution_id` is always the student's own tenant from the canonical context. The DB trigger (`trg_student_notifications_tenant_guard`) derives and forces `institution_id` from the `students` row server-side, rejecting any mismatch (mirrors Phases 6.7/6.8). Cross-student writes are blocked by the FK + trigger; cross-tenant writes raise `F403`/`F404` at the database.
- **Read-state only mutation:** the PATCH route declares no body model; title/message/type/ownership can never be altered by a student.
- **Controlled vocabulary:** arbitrary notification types rejected at schema, service, and DB.
- **No secrets:** no passwords/tokens/credentials stored; no student identity duplication beyond FK references.

## 5. Duplicate / idempotency protection

Academic events must not create duplicate notifications when the same authoritative event is processed more than once.

- **Mechanism:** partial UNIQUE index `uq_student_notification_source_record` on `(student_id, source_record_id, notification_type)` WHERE `source_record_id IS NOT NULL`.
- **Mapping:** a duplicate insert raises a Postgres `23505` / `duplicate key` violation, mapped by the service to the existing error convention `409 NOTIFICATION_DUPLICATE` (`AppError`).
- Notifications without a source record (general admin notices) are not deduplicated — by design.

## 6. Database migration

New file: `supabase/migrations/20260914000000_phase_6_11_student_notifications.sql`

- Inspected existing schema first; no equivalent notification table existed, so a minimal table was added.
- `student_notifications` table:
  - `notification_id UUID PRIMARY KEY DEFAULT gen_random_uuid()`
  - `student_id UUID NOT NULL REFERENCES students(student_id) ON DELETE CASCADE`
  - `institution_id UUID NOT NULL REFERENCES institutions(institution_id)`
  - `notification_type VARCHAR(32) NOT NULL CHECK (… controlled vocabulary)`
  - `title VARCHAR(255) NOT NULL`, `message TEXT NOT NULL`
  - `is_read BOOLEAN NOT NULL DEFAULT FALSE`, `read_at TIMESTAMPTZ`
  - `source_type VARCHAR(64) NOT NULL DEFAULT 'academic_event'`, `source_record_id UUID`
  - `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`
- Indexes: `(student_id, created_at DESC)`, `(institution_id)`, partial `(student_id, is_read) WHERE NOT is_read`.
- Unique partial index for idempotency (see §5).
- Tenant-guard trigger derives/forces `institution_id` and backstops `read_at` consistency.
- Service-role grants consistent with other Phase Admin tables.
