# Revised RPC and custody contract - design only

The SQL is an inspection-only sketch, not an executable/validated migration. Its unconditional stop remains. All public commands are proposed service-role-only SECURITY DEFINER functions with empty search path; private helpers/tables are inaccessible to API roles. Ownership, inherited privileges, RLS, locks and transaction behavior need separately authorized PostgreSQL testing.

These are requester requirements and proposed mechanisms, not formal owner policy approval. Implementation approval has not been granted. Additionally, the SQL rejects all new positive decisions with `AV_SELF_APPROVAL_CONTROL_UNRESOLVED` until a trusted subject-binding control is designed; the positive path below specifies intended behavior after that prerequisite is approved. The oracle models synthetic trusted binding evidence, not an implemented SQL control.

## Shared authority and inputs

The backend derives actor user/Auth ids from verified JWT resolution and resolves one active institution scope from server-owned role assignments. Actor/Auth ids and authority-bearing institution are never accepted from public bodies. Resource ids must belong to that institution. A service credential is trusted infrastructure, not student/staff authority.

Active staff/admin membership plus the **latest explicit individual** `academic_identity.verify` permission event is required for verification/finding commands and retries. Neither existing role permission unions, `*`, `academic_identity.*`, approval/attendance capabilities nor existing Staff-only direct grants qualify. The future application gate must check this private assignment provenance in addition to normal scope guards; the current generic `has_permission` helper is insufficient on its own. No application gate is implemented here.

All commands take an actor-scoped UUID request id and reason. Public transport must reject unknown fields, bound serialized request bytes, and disallow official values, storage metadata, digests, policy configuration, audit/history, expiry, approval/access or email flags. Official positive values come exclusively from the retained entry. UUIDs identify resources and never confer permission.

## Individual permission assignment/revocation

`public.manage_academic_verifier_permission` inputs:

| Input | Meaning |
| --- | --- |
| `p_actor_user_id`, `p_actor_auth_user_id`, `p_institution_id` | Backend-derived identity/scope. Actor must be an active institution admin. |
| `p_mandate_id` | Active owner-created `permission_grantor` mandate for this actor/institution. Admin status or verifier capability alone cannot delegate. |
| `p_target_user_id` | Explicit selected user. Self-targeting is prohibited for both grant and revoke; an alternate grantor handles it. |
| `p_expected_revision`, `p_request_id` | Expected target permission head (zero if none), and actor/command request key. |
| `p_grant`, `p_reason`, `p_policy_id` | Grant/revoke and reason. Grant requires complete latest approved policy and active tenant-local staff/admin target. Revoke needs an existing granted head but no active target or current policy. |

Append immutable `permission_events` plus existing audit and receipt. Return `event_id`, `target_user_id`, `recorded_revision`, `head_revision`, `replayed`. A role or target change cannot silently substitute another user. Revocation history is retained; later regrant requires the current expected revision and new authorization.

Each event retains exact permission code, institution, selected target, grantor/revoker user and Auth ids, owner mandate, target-role snapshot on grant, DB timestamp, reason, expected/new revision and audit reference. The model checks this provenance rather than treating an actor's permission strings or admin role as an assignment. Decisions retain the authorizing event snapshot. Mandate/evidence strings cannot themselves establish owner approval.

Owner-designated mandate bootstrap, replacement and revocation are privileged reviewed operations with owner evidence and audit under the institution lock. No runtime user can appoint themselves. Mandate revocation blocks new management commands and retries but does not retroactively cancel earlier independently assigned verifier permissions. Explicit assignment review/revocation is required. Named actors, emergency succession and any dual-review requirement remain undecided; no mandates or assignments are seeded.

## Accepted immutable source versions - custody prerequisite

No upload/acceptance/invalidation RPC is implemented in this package. The separately reviewed trusted custody writer must implement this contract before enablement:

1. Receive bounded original bytes through an authenticated private upload path after checking active institution staff/admin membership, actor/Auth pairing and explicit owner `register_uploader` mandate. Recheck this authorization at acceptance. Compute SHA-256 and byte length on the server. Persist an immutable, private object and concrete storage version. Do not accept a client hash as authoritative, infer trust from a filename/reference/checksum, or route through generic documents/RAG/publication.
2. Under the institution lock, validate current custodian user/Auth/tenant and owner `register_custodian` mandate, complete approved policy/governance and authenticity procedure. Check the approved uploader/authenticator separation rule. Inspect restricted retrievable handoff/signature/other approved evidence binding the institution, official issuer/custodian and exact copy; retain method, provenance description, evidence reference and authenticating actor/time. Nonempty strings alone are not authentication. Capture issuer name/version and effective/as-of date where available. Otherwise retain NULL plus attested missing-metadata reason; never substitute upload date. The final freshness policy may refuse sources lacking required dates even if authenticity is established.
3. Retain mandatory internal source-version UUID, institution, available issuer metadata, private bucket/key/object-version, SHA-256, length, uploader and authenticator user/Auth ids, upload/receipt/acceptance times, mandates, import-confirmation evidence and expected entry count. Import **all** confirmed raw string entries in the same custody transaction and append existing audit. Validate required kinds, locators, normalization and duplicate register/person/roll values; refuse ambiguity. Upload precedes the DB transaction; failed custody never creates an accepted partial source.
4. Persist an entry id, unique version-local exact locator and raw `official_person_key`, mandatory `register_number`, optional `university_roll_number`. No numeric conversion or zero-padding invention. Custodian confirms OCR/parsed values against the original copy and records `confirmed_original_strings`; unreviewed, formula/numeric coercion or OCR ambiguity is refused, including ambiguous strings. Exact locator syntax and source integrity read-back schedule are owner decisions.
5. Source invalidation appends `source_invalidations` and existing audit under the same lock after live custodian authorization. Retain actor/Auth, mandate, DB time, reason and incident evidence reference. It needs no new positive policy approval, never removes bytes/history, and cannot be reversed. The proposed conservative guard makes dependent positives unusable in every future current-state read after invalidation commits, independent of cancellation jobs, while retaining their original decision status. Authorized withdrawal appends an explicit withdrawn head referencing prior evidence. New accepted version and independent verification/correction are required for recovery; no decision silently changes identity or source.

Replacement/supersession only adds a retained source version; it does not transfer, overwrite or automatically revoke decisions. Institutional remediation and source freshness rules remain owner decisions. Source age, missing dates, expiry/no-expiry, renewal, supersession and effects on old decisions must be explicit before enablement. A missing required freshness configuration refuses every new positive; no duration is supplied by this proposal. Synthetic bounded/no-expiry examples exercise mechanics only.

The SQL retains required metadata/FKs and denies direct service-role table writes; it cannot prove authenticity, server hashing, storage immutability or custodian diligence. Owner operations must also use the common lock order. Mandate revocation does not erase past authentic custody acts; a compromised copy needs explicit source invalidation.

## Identity decision command

`public.record_academic_identity_verification` inputs:

| Input | Meaning |
| --- | --- |
| Actor/Auth/institution | Backend-derived and independently rechecked as above. |
| `p_identity_id`, `p_expected_revision`, `p_request_id` | Stable tenant identity UUID, exact reviewed head, unchanged retry key. New `verify` uses revision zero. |
| `p_operation`, `p_reason` | `verify`, `reverify`, `correct` or `withdraw`, plus explicit reason. |
| `p_policy_id`, `p_source_version_id`, `p_entry_id` | Required for positives; exact latest complete policy and accepted, non-invalidated source/entry. All must belong to this institution. |
| `p_student_id` | Optional explicit tenant-local profile link for positive verification. NULL preserves an existing link; no unlink/reassignment is allowed. |

Positive decisions load every raw entry identifier, canonicalize using approved rules and record all supplied source kinds as checked. Required kinds are fixed to person key and register number; roll remains optional. Source entry count and overlapping source keys are rechecked. No caller-supplied subset can hide a source roll number.

Every new positive must satisfy the exact subject-binding invariant below. Self-approval exclusion alone is insufficient: the selected account must positively agree with independently proofed ownership evidence. The model now checks that agreement; SQL continues to refuse every new positive unconditionally. No production binding writer/resolver or institutional approval is supplied.

Compare actual register AND roll values across every tenant-local profile and every section roster. Register is primary; no roll-only/profile student-number matching. More than one profile, disagreement on any overlapping field, candidate roll absent from source, wrong/missing explicit profile link or incompatible roster link refuses success. Multiple consistent section rosters are allowed and never rewritten. Missing source roll is acceptable for an account-independent person if no related legacy record requires reconciliation. Missing values never establish a match. Legacy aliases/backfill, names, email, approval and attendance do not prove official identity.

`reverify` requires the same canonical values and association on a positive current head; changed register values require explicit `correct`. `correct` requires new independent entry consultation and binding validation, preserves the historically established person and complete account-association tuple, and may restore a withdrawn identity with that same tuple using valid source/policy. Ordinary commands cannot attach an account to a previously unlinked positive, change profile/user/Auth identity or adopt a different association revision. Account attachment/recovery/replacement and wrong-person repair need a separate owner-approved workflow; none is supplied. All prior positives reserve historical identifiers. A conservative `correct` cannot alter existing student/roster data to make its checks pass.

`withdraw` requires a currently positive head and current explicit verifier permission, but source/policy/entry/student inputs MUST be NULL. It references the prior decision's evidence/policy/source, appends withdrawn head, removes current claims and preserves historical ownership and link. It works despite source invalidation or unusable/new policy. Repeated withdrawal of an already withdrawn head is refused. Correction/withdrawal reviewer or dual-control requirements remain an owner blocker; the sketch currently enforces one authorized verifier plus reason.

The self-approval prohibition applies to positives. A currently authorized verifier may withdraw their own prior decision without asserting a new identity; additional withdrawal review/dual control remains undecided. Rejection of an unverified candidate uses the finding command and can neither withdraw an established positive nor create a withdrawal for a never-verified identity. Identifier reuse/transfer and exceptional reassignment remain unresolved even after withdrawal; the guard reserves historical ownership and reports review required, not approved lifetime uniqueness.

Return `identity_id`, `decision_id`, `recorded_revision`, `recorded_decision`, `head_revision`, `replayed`. There is no eligibility/token/account/approval/role/email flag. Historical verified retry results are not current eligibility evidence.

## Exact subject-binding invariant (normative proposal)

For a **new** `verify`, `reverify` or `correct`, all of the following must hold together. Missing owner policy or unavailable trusted state means refusal; matching register/roll values never repair an ownership failure.

1. The currently authenticated verifier has the exact individual `academic_identity.verify` assignment and active institution scope. Actor user/Auth identity comes from trusted authentication resolution, not the request. The selected accepted source version and entry belong to that same institution, contain a mandatory register number and identify the established official person under an approved person-key interpretation.
2. A current approved binding names that exact institution, official person key, source-version id and entry id. Its immutable structured `BindingEvidence` receipt must equal the retained receipt in the trusted proofing registry; its `SubjectBinding` approval must equal the retained approval in binding history and be the selected current binding. An arbitrary reference string, pasted account id, boolean, copied identifier or caller-created receipt cannot authorize anything. Missing/incomplete/unregistered/altered evidence, revoked receipt/approval, unapproved method/mode or a different source/entry refuses.
3. In `account` mode the receipt specifies **one exact tuple** `(institution, person key, profile id, user id, Auth id, association revision)`. That tuple must equal both the authoritative current account association and the selected profile's current user/Auth/revision; all values are required. The directory association must be active, and conflicting/additional associations for that subject refuse. Authentication proof of the exact account AND independent institutional proof that the human subject owns the official entry are required; neither account control alone nor knowledge of register/roll values proves that relationship. Unknown aliases/multiple accounts are unresolved, not first-match selection.
4. In `no_accounts` mode all account/profile/association-revision fields must be NULL, the command must select no profile, and the authoritative subject/account directory must contain no association for that person (including inactive retained associations). Separate non-NULL `directory_baseline_id` and positive integer `directory_generation` must identify the attested institution directory state described below. This mode requires a separately approved method/mode and a complete, independently reviewed absence search, never an empty caller list. It records an account-independent subject only, confers no account entitlement and cannot later acquire an account through ordinary correction. Conflicting matching legacy profiles still fail the existing comparison contract. Whether institutions permit this mode remains an owner decision; fixtures only simulate explicit permission.
5. The receipt's collection time and explicit validity end, the approval time, and post-wait current time must satisfy `collected_at <= approved_at <= now < valid_until`. Missing validity configuration cannot mean unlimited validity. Approval must use the latest complete policy, including `subject_binding` governance, and an explicitly allowed method/mode. Establishing and reviewing actors require live server-resolved user/Auth pairs, active institution scope and separate explicit institution-bound authority. The model uses synthetic `subject_binding_establisher` and `subject_binding_reviewer` mandates; real appointments, acceptable proofing/search procedures, validity rules and independence policy are **not approved**. The conservative model refuses if establisher/reviewer are the same user OR Auth identity, either is the subject, or the verifier is the subject, establisher or reviewer. It rechecks those actors/mandates for every new positive and usability read; authority revocation makes evidence unusable without rewriting history. Institutional succession/revalidation policy still needs approval.
6. Record the complete receipt, approval, policy and observed association snapshot with the decision. Every historical positive must have binding evidence and the same association tuple as the new positive, including NULL fields and revision. A new receipt or account link cannot silently migrate an existing verification. An explicit new positive may adopt fresh approved evidence only for that unchanged tuple. `current_usable` must revalidate source/entry, live binding/proofing/reviewer authority, live account/profile association and existing conflict checks, and require the exact recorded binding/approval snapshot still to be current. Reapproval alone does not refresh a decision. Changed account/Auth/profile/person association, revision, expiry or revocation returns false while preserving the recorded decision. Historical retries still return their recorded result after current verifier authorization; they perform no new decision and never imply current usability.

### Persistent no-accounts directory invariant (proposed control; not owner approved)

An absence receipt binds the exact institution/person/source/entry to an immutable directory baseline id and monotonically increasing **institution-wide** generation. This generation is distinct from the nullable per-account association revision. A positive integer, reference string, empty association map or `complete=True` alone establishes neither completeness nor authority. The model requires an explicitly registered structured `DirectoryBaseline` attestation, live server-resolved writer user/Auth and a dedicated synthetic `subject_directory_writer` mandate. Fixtures assume an upstream authority honestly established full directory coverage and reliable historical continuity; no real completeness discovery, authentication, attestation inspection or owner appointment is implemented. With no such trusted prerequisite, refuse; do not bootstrap completeness from observed emptiness.

The conservative sequential proposal uses immutable `DirectoryRevision` snapshots linked by consecutive generations, an exact current head, a separately retained highwater continuity anchor and a retained bootstrap receipt. The first generation records the attested baseline; each subsequent generation retains the complete institution association snapshot, operation, writer user/Auth/mandate, time and reason. Deletion retains preceding snapshots as tombstones. Complete policy must include `absence_directory` governance. These are proposed technical representations, not an approved operational schema, storage format or retention policy. An unrelated subject's change in the same institution invalidates absence evidence conservatively; another institution's generation does not. Granularity and the cost of institution-wide invalidation require owner approval before implementation.

Every association creation, removal, reassociation, activation/deactivation, account/Auth/profile replacement, recovery or directory restore must advance the generation under the common writer/reader transaction protocol, even if the final values equal earlier values. Retain before/after history; never reuse a generation, reset the highwater, overwrite a baseline or erase a tombstone to recreate apparent absence. All real writers must participate, including external identity and legacy/recovery workflows. A new baseline id cannot renew an old receipt. The generation comparison is mandatory at absence-evidence approval, every new `verify`/`reverify`/`correct`, and every current-usability read; directory state time must precede collection, and normal evidence validity/authority/source checks still apply. Retain the baseline/generation in the decision's exact receipt/approval snapshot.

The receipt must name the **same baseline and generation as the current reliable head**, with complete baseline authority, consecutive retained history, a bootstrap receipt and a head/highwater/live-snapshot match. Missing/invalid generation, incomplete/unregistered/foreign baseline, missing/truncated/rolled-back history or anchor, untracked live rows, revoked writer authority or an unresolved integrity incident refuses. The model latches observed directory integrity/completeness failures in a separate `directory_unreliable` security marker, including detection during current-usability reads. Deleting untracked rows or restoring missing history therefore cannot heal that observation. Decisions/history/claims/receipts/successful audit remain untouched; the security latch is the intentional read-side state change, not a new positive or proof of durable incident delivery. An incident cannot be cleared by an ordinary directory update, empty map or rebootstrap. Real completeness loss must mark state unreliable at its authoritative source. If every trusted baseline/journal/head/highwater/bootstrap/incident store can be rolled back together, these in-memory consistency checks cannot detect that coherent rollback or an entirely unobserved out-of-protocol change cycle: durable external continuity/restore guarantees and participation of all writers are explicit prerequisites, not claims of this model. Missing trusted continuity must keep positives disabled, not reset generation to one.

Within a retained reliable lineage, generation mismatch permanently disqualifies the **old** absence proof without needing a batch revocation job. This persistence depends on the continuity trust boundary above; it is not protection against coherent rollback of every trusted input. Explicit receipt/binding revocation remains available and is cumulative, not an alternative to generation checks. After association creation then deletion/reassociation/recovery, the directory may look empty again, but its generation differs and retained snapshots still record the association. Removing a conflicting legacy row changes neither fact. Historical decisions/claims remain retained; current usability is false and failed new positives append only a separate denial. Historical replay stays historical and does not update the receipt or head.

There is no approved policy for a previously associated subject to become eligible for `no_accounts` again. Therefore every new positive and usability read also refuses when any retained directory snapshot records an association for that subject, including inactive associations. A fresh generation-matching receipt or its approval cannot authorize that transition; approval attribution alone is not positive eligibility. This conservative `absence_history_requires_review` guard requires a separate owner-approved reconciliation/recovery workflow. An unrelated subject's change may be addressed only through fresh independently established/reviewed evidence and an explicit new positive for the unchanged subject/account tuple; reapproval alone never refreshes a historical decision. No ordinary command attaches or transfers an account.

**Unresolved owner responsibilities:** name the trusted directory writer and revision/continuity authority; approve authoritative coverage, alias/account inclusion and absence-search guarantees; specify bootstrap and durable anti-rollback/restore/tombstone controls; choose generation granularity, storage/retention and all-writer coordination; assign incident detection, reliability marking, evidence invalidation and recovery responsibilities; decide previously associated subjects, reassociation/recovery/replacement and authority succession. No real appointments, approved mechanisms or positive SQL implementation are supplied. Until those decisions and implementations exist, both SQL refusals remain intact.

### Strict generation validation and restoration characterization

The separate directory head generation, every retained journal generation, highwater, no-accounts receipt generation and writer expected generation must each be an actual positive Python integer in the offline model (`type(value) is int`, excluding booleans). Validate the head independently **before** record equality or numerical comparisons: `True == 1` and `1.0 == 1` cannot establish a trusted head. NULL/missing, strings, zero, negative, fractional/numeric substitutes and inconsistent values refuse. A valid registered receipt cannot bless a malformed head or journal. Directory state faults latch `directory_unreliable`; malformed/stale receipt or expected-command generation refuses without manufacturing a directory incident when authoritative directory state itself is reliable. A current-generation receipt collected before that state's recorded time also refuses.

Independently validate the separate head's **association rows** before comparing them with journal or live rows. Require the tuple container and complete `AccountAssociation` fields: institution, subject/person key, profile, user/account, Auth ID, revision and active flag. Institution must match the exact scope; all five identifier strings must be bounded and nonempty under the existing model string checks. Association revision must satisfy `type(value) is int` and `value > 0`; active must be an actual boolean. Reject missing fields, malformed row/container values, booleans including `True` equal to retained revision 1 and `False` equal to invalid zero, floats and numeric strings. Zero is not a valid retained association revision. Dataclass annotations and equality supply no type validation. Validate retained journal association rows before comparisons as well. Required head fields must exist; malformed internal state must raise a refusal and latch the marker, including during current-usability reads, without altering decisions, history, claims, receipts or successful audits. Well-typed head/journal/highwater/live contradictions still refuse. An invalid receipt alone remains distinct from authoritative-state corruption.

The model's ordinary `restore` operation is a proposed trusted-writer transition: retain preceding snapshots, increment generation exactly once, retain audit/actor attribution and keep account association revisions above their historical maxima where restoration changes/reasserts them. Even restoring an identical empty snapshot increments generation. This does not authorize any real backup-restoration workflow. Normal refusal preserves decisions, claims, receipts and successful audit; directory integrity faults may additionally latch the separate security marker. Refused bootstrap attempts now also retain a separate attributed `directory_initialize` denial, with synthetic observed time, baseline reference and reason code. No durable audit, authentication/time source or recovery transaction is implemented by that event.

For **populated restore**, every restored row must exceed all retained association revisions sharing its profile, subject, account/user or Auth ID, even when its current tuple is unchanged. Reinstating an older account tuple at its earlier revision or at a related account's retained maximum refuses specifically as `directory_association_revision`; valid authority, expected generation, row schema and chronology must already pass. This request refusal preserves directory and decision state, appends an attributed writer denial and does not by itself mark the directory corrupt. A strictly higher revision can support the synthetic writer transition: append history, advance generation and audit, while preserving prior decisions/claims/receipts. Old absence proof stays unusable in that retained lineage. This does not authorize account reassociation in a verification decision or resolve the owner's restoration/continuity policies.

Partial and mixed restoration must refuse whenever head/journal/highwater/active baseline/live snapshot/receipt cannot establish one consistent trusted state. Restoring highwater independently, or replacing head alone with a boolean-equal value, is not trusted continuity. Detecting a mismatch latches an incident: later restoration of the correct fields cannot clear it. Ordinary create/remove/reassociate/recover/replace/activate/deactivate/restore and bootstrap cannot clear a marker. Bootstrap must refuse even after other directory markers and rows are removed, while a valid baseline, live authority and the incident remain. There is no ordinary incident-clear or reconstruction command; authorized recovery remains a separate unresolved owner workflow.

The offline suite deliberately characterizes **coherent privileged rollback of every model-held input** by restoring the entire oracle state, including baseline, directory/head/highwater/bootstrap/incident state, proof/approval registries, decisions, claims, receipts, successful audit and denials, to a previously usable snapshot. With no independent witness surviving, the model **cannot distinguish it from that earlier valid state**: current usability may be true again, historical replay adds no writes, and even later audit/denials have been rolled back. This is a passing limitation-characterization test, not a guarantee of permanent invalidation or history preservation under privileged rollback. The model does not detect the restore and no denial is expected for an undetected event. An explicitly supplied synthetic external unreliability signal forces refusal/latching, but it does not implement or validate an external authority. Real continuity loss or unknown restoration status must fail closed at the authoritative boundary; no operational mechanism or owner approval is invented here.

### Evidence provenance and collection-to-commit boundary

The accepted source must exist before evidence collection (`source.accepted_at <= collected_at`). Within the institution, another directory association sharing the selected profile, user or Auth id with a different subject also refuses; a single account cannot be borrowed to verify a second person. The model refuses missing historical binding snapshots rather than treating old verification as sufficient evidence for an upgrade.

The trusted proofing writer must inspect an owner-approved institutional identity/ownership procedure and, for account mode, validated authentication of the exact subject user/Auth pair. It retains restricted retrievable proof/session and institutional evidence, issuer actor/Auth/mandate, method/mode, exact subject/source/entry/association tuple, collection/validity times and immutable receipt id. An independently authorized reviewer inspects the same evidence and approves its exact version under a recorded policy. A filename, checksum or reference containing an account name is only a locator. The fixture's `binding_evidence`, `binding_actors`, method/mode allowlist and `account_associations` stores **assume** the upstream evidence/authentication has been established honestly; no external inspection, authentication, completeness proof or durable storage is implemented. `approve_binding` models authorization and attribution of that future approval, not a shipped endpoint. No actor can self-appoint through it.

The future transaction must pin the reviewed binding/receipt version and expected subject/profile/account association revision in the server-held command; these are not caller ownership assertions. After the institution lock, acquire participating subject/establisher/reviewer/verifier user rows in UUID order before authorization rows, then identity/head, policy, source/entry, binding/receipt and association records in one reviewed deterministic protocol. Recheck the exact reviewed tuple, authority, validity, revocations and expected head after waits and immediately before commit; stamp DB time after waits. All profile/account/Auth/recovery/subject-association and evidence writers must coordinate and increment association revisions so even change-away-and-back cannot reuse evidence. No human/network proofing inside the transaction. Reads/issuance need a compatible protocol too. If existing writers cannot meet it, positives must stay disabled. The final lock design and PostgreSQL races remain unverified; sequential deep copies in the oracle do not simulate this guarantee.

Refusal preserves decision/head/claims/receipts and prior successful audit history. The model records a separate security-denial event for refused decision/approval commands with actor/Auth, institution, operation, request/resource references, reason code and observed time. This is a proposed logging boundary, not proof of durable or atomic denial audit; failed SQL cannot commit that event in its rolled-back transaction. Real event size limits, redaction, access controls and durable delivery require implementation and validation. Evidence retention/access rules apply to approvals, receipts and denials too. Candidate rejection and authorized withdrawal do not assert new positive ownership and retain their separate semantics.

### Owner decisions that block a safe positive contract

Owners must explicitly designate who may establish/review bindings, approve proofing and authenticated-session provenance, authoritative directory completeness and revision rules, method/mode allowlists (including whether no-account subjects are permitted), validity/renewal/revocation/succession rules, independence/dual control and lawful retention/access. They must also decide account attachment, reassociation, recovery, replacement and identity correction; ordinary commands refuse these changes meanwhile. Existing register freshness/replacement, normalization/Unicode/collisions, person-key stability, identifier reuse/reassignment, authenticity and evidence/audit retention questions remain unresolved. Without these decisions and the trusted writers/readers/locking design, the invariant cannot be established for real accounts: the SQL refusal must remain intact.

## Candidate findings are a separate command

`public.record_academic_candidate_finding` accepts backend actor/Auth/institution, request id, accepted non-invalidated `p_source_version_id`, `p_searched_locator`, `p_finding` (`rejected_match`/`unresolved`), bounded raw `p_observed_values`, reason, optional exact entry, candidate profile and context identity.

An entry id requires that entry's exact locator. Without an entry, the locator identifies the consulted range/search; this is staff attestation, not a computed assertion of absence. Observed values are bounded register/roll strings, never official ownership assertions. Candidate and context references are tenant-local. Append only finding, audit and receipt; **never** change an established identity head, claims, legacy rows or approval. Return only finding id/type/replay status. Missing current positive policy does not prevent recording a negative finding with current verifier authorization and usable accepted source.

## Lock order, races and retry boundary

1. Check service caller, structural inputs and READ COMMITTED. Set draft 5-second lock ceiling; outer caller must set a statement/transaction deadline before invocation. Exact operational budgets remain undecided. Acquire institution transaction advisory lock shared by decision/finding/permission commands and reviewed policy/mandate/custody operations.
2. SHARE-lock `user_roles`, then `roles` for all commands, closing membership/scope insertion phantoms without modifying legacy writers. Positive decisions additionally SHARE-lock `students`, then `faculty_attendance_rosters`. These are cross-institution locks and must be assessed for deployment volume.
3. Lock active institution, then participating users in UUID order (management actor/target), role memberships/roles, capability and authorization records. Reject stale actor/Auth pairing, ambiguous scope, inactive user/tenant/role or missing/revoked exact assignment. Management checks mandate; revocation does not check target activity. Source/mandate invalidation uses the institution protocol; capability/user/tenant updates must serialize on row locks.
4. Reauthorize BEFORE checking command-scoped idempotency receipts. Same payload/key returns recorded result plus actual current head. Changed payload conflicts; replay never reopens a withdrawn head. An invalidated-source historical retry may return recorded success without any current-eligibility assertion.
5. Lock identity/head, resolve latest policy and accepted source/entry for positives, compare all relevant identifiers. New command with stale expected revision refuses; do not automatically rebase staff decisions. Policy/person-key interpretation changes require a collision-reviewed design, not silent reconfiguration.
6. Take DB time after waits, derive expiry only from explicit policy, and append existing audit, event/decision/finding, claims/head and receipt in the same intended transaction. Deferred head FK must reject incomplete state at commit. No error handler swallows audit failures.

Required ordering: if revocation commits before a protected command acquires the institution lock, that command (including replay and withdrawal) must observe the revoked assignment and refuse. A command holding that lock may finish before a waiting revocation; revocation does not retroactively erase it. Grant/regrant commits first permits a later command only after all current checks; verification before grant refuses. Grant/revoke races use expected permission revision, with no lost update. This is a linearization requirement for PostgreSQL testing, not measured behavior or immediate cancellation of in-flight work. All protected writers must follow the common protocol; membership/capability changes need compatible locks. Future reads require their own authorization and transaction contract.

Existing writers may acquire locks differently; deadlocks/timeouts are possible, not proven absent. They must abort the entire command. After uncertain disconnect/timeout, check outcome and retry identical key/payload; never report success on uncertainty. Avoid uncontrolled generic retry of the synthetic stale-head `40001`. Exceptions cannot also commit denial audit in the same transaction; future application denial logging uses the existing server security-event path.

## Error and read contracts

* `42501`: generic 403, no tenant/resource/evidence details.
* Revision/resource/idempotency/identifier/link conflicts: bounded 409 requiring authorized review; never raw constraint errors.
* Invalid/unconfigured governance, evidence/date/type/size: safe 422 or 409.
* Missing mandatory register number, roll-only substitution, ambiguous extraction or unknown normalization: refuse without creating a decision/claim; no guessing or automatic alias mapping.
* Missing required freshness/owner policy or subject binding: fail closed with a bounded policy/review-required response; synthetic approval references cannot resolve it. The SQL's `AV_SELF_APPROVAL_CONTROL_UNRESOLVED` maps to a generic refusal while its guard remains.
* Invalidated source: refuse new positives/findings; authorized withdrawal remains possible. Historical replay reports recorded result only after live authorization.
* Deadlock/lock timeout/unexpected DB failure: safe retryable/uncertain result, unchanged command/key, no partial success assertion.

Search, history and current-state projections need separately authorized tenant-local reads and redacted responses; no direct table access is granted. A future eligibility reader must lock/check exact positive head, source not invalidated, complete owner freshness policy using DB time, and current conflict-free profile/roster relationships. Policy supersession, source age/supersession and expired-claim handling are explicitly undecided. Existing accounts/rosters remain unverified absent independent current positive evidence; verification itself changes no account/role/email/access state.

Current usability also requires the exact recorded binding/approval, usable proof receipt and current directory/profile tuple described above. Historical positive status or a replay is not a substitute; changed associations and reapproval do not silently transfer or renew verification.

## Account-mode strict validation and live collection

Account-mode new positives and current-usability reads must validate the authoritative directory through `_directory_state`, including required head/journal/live schema, exact scope, history/highwater/baseline consistency, live writer authority and the retained integrity marker. Refuse and latch; preserve domain/history/claims/receipts and successful audits. Decision/writer/bootstrap denials retain their existing attribution contract. Current reads latch and return false without creating a decision denial. Repair, ordinary writer operations and bootstrap cannot clear an observed incident. Foreign institution partitions are checked when that institution is read, not selected by an unchecked row's claimed institution.

Validate proposed writer rows outside the authoritative-state incident path. Actual persisted association changes must still use the trusted writer/revision protocol; historical tuple migration remains refused. Named directory/revision owners, complete account/alias/writer coverage, real proofing/reviewer authority, durable history/independent continuity and authorized incident recovery remain unresolved; no operational recovery mechanism or owner approval is supplied.
