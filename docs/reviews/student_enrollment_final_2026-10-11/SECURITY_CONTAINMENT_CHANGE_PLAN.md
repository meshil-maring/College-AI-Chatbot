## 2. Prepare a transactional review-only candidate

After authoring approval, prepare SQL in the review directory, separate from production auto-discovery. Keep its own review stop/rollback until its exact bytes receive execution approval. Preconditions must validate target PostgreSQL version, object identity/type/owner, existing guard signatures/bindings, expected source chain and overload set. Unknown variants fail closed; do not use CASCADE to revoke/destroy dependencies without review.

The eventual installed order inside one approved transaction is:

1. Assert creator/role/object assumptions and collect the approved ACL/policy/trigger comparison without payload/credential dumps. Catalog collection itself is separately authorized; do not run it now.
2. Remove unsafe function defaults at their correct global/schema scope. Existing functions still require explicit repair. Do not expect schema-specific revocation to subtract global PUBLIC defaults, or CREATE OR REPLACE to reset ACLs.
3. Contain exact six sensitive signatures and reviewed client helper identities, keeping explicit existing service command grants. Preserve already denied overloads, the private renamed assignment implementation, default arguments and return contracts. New functions revoke PUBLIC/client/service grants before final explicit grants, within the transaction.
4. Contain admin audit mutation privileges, including column UPDATE/utility privileges/grant options, and complete client denial/RLS. Retain SELECT/INSERT and the existing rejecting row trigger. Create one distinct rejecting statement TRUNCATE trigger with an owner-only helper. Never grant service audit mutation as a workaround for testing or retention.
5. Contain authority/legacy academic table and column access; enable missing RLS. Preserve current scoped policies/guards and narrow service read/write support required by the confirmed request-role contract. Reassert existing master/direct-grant denials after broad grants. No broad public-schema service revocation.
6. In a separately reviewed body change, add compatible service-request assertions at selected public command boundaries, and fully qualify unsafe definer lookups. Do not require human JWT context inside ordinary integrity triggers or simply clear an unqualified body's search_path. This step can be a second candidate, but full definer-security acceptance remains gated by its assessment.
7. Postflight the exact source/catalog allowlist: effective PUBLIC/client/column/inherited grants, service audit denial, expected service command entry points, private helpers, owners/search paths, RLS and guard definitions. Report unexpected overloads/bridges as blockers, not incidental changes.

Preserve error handling and audit failure semantics: failed audit insert must abort state mutation. Do not disable integrity triggers, relax tenant/actor checks, alter privileged client headers, change role memberships or install an ad hoc guard-bypass GUC. No backfill, migration of enrollment data or historical correction belongs in this candidate.

## 5. Rollback and operational limits

The future containment transaction must roll back entirely on pre/postflight mismatch. An error in the proposed candidate is corrected and reviewed before retry; no partial grant window or `CASCADE` workaround is allowed. Keep grants/revocations and any function creation in one transaction.

After installation, a compatibility rollback must retain client denials and audit destructive denial. Restore only reviewed necessary service read/insert/command access or correct safe policy/body behavior; never restore the old unsafe defaults or blanket grants. Store prior catalog ACL/policy/trigger definitions as controlled comparison evidence, not a script to automatically reopen access. The maintenance owner remains powerful and requires an explicit retention/reset procedure outside untrusted roles.

Existing data is unchanged by this proposal. ACL/RLS rollback cannot undo already authorized actions, flattened episode mappings, external deliveries or historical corruption. Enrollment lifecycle rollback is a separate plan and cannot collapse multiple episodes/attempts into one identity membership. No operational cutover, historical repair, remote application or deployment is authorized here.
