## Deterministic mapping algorithm

1. Capture original row snapshots with student PK, source hash, exact institution/program/year, legacy status/approval/archive flags and legacy dates. A migration recorded_at is the time of observation, never admission time.
2. Validate account link, institution existence, program department ownership and year ownership. Collect each identifier as text; run normalized collision analysis across distinct students and across kinds used by untyped login. Same person/multiple subject rosters is not a collision.
3. Complete, verified documentary admission data maps to an evidenced episode. A registration date alone is insufficient. Approved legacy account does not automatically mean approved admission. Map `inactive` only with a formal institutional interpretation; otherwise quarantine.
4. Without verified admission chronology/approval/program, create a `legacy_unresolved` snapshot via a later import routine, mapping unresolved/ambiguous; retain original values in a creation snapshot event and grant no operational entitlement. Do not insert a guessed placement. The core admin RPC intentionally cannot claim migration authority.
5. Establish placement only from evidenced year/semester, curricular ordinal, attempt and actual interval. Master semester start/end are academic calendar bounds, not proof the person attended for the entire period. Unknown year/semester/dates remain candidate evidence outside canonical placement rows.
6. Match historical records by their own institution, program/offering/year/semester, student or validated roster identity, actual attendance/conducted date and documentary attempt. Require exactly one supported episode/attempt. Never use newest active enrollment as tiebreaker. A supplementary result's examination date can fall outside its original placement interval; verified assessment lineage controls the match.
7. Zero candidates or multiple candidates -> explicit unresolved association, privileged reconciliation queue, no guessed FK. Student access to unresolved legacy own published data may use a separately approved compatibility exception with frozen original tenant and no current eligibility implication; default new historical endpoint omits it.
8. Idempotent import operation ID is derived deterministically from mapping version + source PK + source hash (not a random number on every run). Changed evidence creates a new corrective operation referencing the prior event, never overwrites provenance. Preserve an inventory for rejected collisions even if no canonical identifier row can be created.

## Historical record association design

This core draft does not ALTER academic tables. A later compatibility migration must add actual FKs/guards to the following exact owners, preserving primary keys:

| Existing owner | Required association and invariant |
| --- | --- |
| `student_attendance` | Optional episode/placement while mapping unresolved; verified rows require same student, frozen tenant, matching offering context and attendance date within evidenced participation. Preserve immutable student/section/year/semester. |
| `faculty_attendance_rosters` / `faculty_attendance_records` | Roster links stable identity; per-record participation resolves episode/placement at session date. A single roster-level current episode is insufficient for a subject roster spanning a leave or repeated interval. Session/offering owns tenant. Unregistered record remains unlinked. |
| `test_results` | Workflow test/roster identity retained; bind original assessment attempt and enrollment, snapshot publication independently of current roster status. Legacy unique key incorporates actual assessment identity/attempt. Supplementary assessment references original curricular attempt. |
| `student_results` / `student_result_items` | Parent owns student/tenant/program/placement and publication edition/type. New uniqueness includes attempt + assessment/publication edition, not only year/semester. Items inherit; section/course must agree with parent context. Preserve old publication values; corrections explicit. |
| `student_notifications` | Optional original episode and typed event reference; original source institution and recipient immutable. Unknown/general notification does not require fabricated episode. Deduplication uses source/operation identity. |

Replace, rather than duplicate, `student_attendance_tenant_guard`, `student_results_tenant_guard`, `test_results_tenant_guard`, `trg_student_notifications_tenant_guard`, `faculty_attendance_identity`, `reconcile_faculty_attendance_roster_student`, `reconcile_faculty_test_roster`, and `refresh_student_test_visibility` / `test_student_visibility`. ## API and atomicity contract

Proposed v2 context-list response: own opaque enrollment handle, institution/program labels, lifecycle/admission decision, optional placement handle/year/semester labels, `context_revision`, `current_eligible`, `historical_eligible`, safe incomplete-data reason. Current context defaults to the unique active approved episode with placement valid on today's IST date; on-leave can be displayed but grants no current participation. With zero eligible episodes show a pending/history-only state, never guess.

Student selection is a filter: server resolves own identity and rechecks the selected episode/placement and record tenant on every call. Unknown/foreign handle -> safe 404; no side-channel foreign labels. Core admin mutation endpoints accept only action-specific fields, expected_version and operation_id; server supplies actor and tenant and rejects unknown authority fields. The SQL draft's generic JSON envelope is internal, never exposed directly to untrusted clients.

Lock ordering for final adapters: operation key -> sorted `academic-setup:<institution>` locks -> student identity -> ascending enrollment UUID rows -> any required sorted `attendance:<institution>` lock/roster rows. Existing attendance/academic routines currently use other lock orders; audit and harmonize these before integrating. Required consistency writes and notification intent must be in the same database transaction; notification network delivery and Auth calls cannot be included. A failure at event, audit, mapping, reconciliation or intent insert aborts the public DB transaction. Never swallow it and report success.

## Rollback limitations

There is no lossless rollback from two institutions/programs/admissions/attempts to one legacy membership row. Preserve all episode/event/identifier/placement and academic primary keys. Security grants are not rolled back to exposure. After operational multi-episode data exists, the safe fallback is disable affected transitions, preserve correct historical reads and forward-repair. Backup restore is an incident decision with explicit reconciliation of writes since backup, not an automatic schema inverse. No production/remote execution is approved by this package.
