## 3. P01: token binding and durable single-use reservation

### Representation and options

Proposed logical state names and command names in this report are design vocabulary, not approved SQL signatures. The recommended model extends an institution invitation with a monotonic `token_generation` and an **accepting** status, backed by a durable acceptance operation and append-only operation events. An operation records invitation kind/ID/generation, immutable tenant/role/normalized recipient/issuer snapshot, purpose, trusted caller/principal binding, opaque idempotency identifier, claim time/deadline, canonical application/Auth IDs when known, provider step/outcome category and finalized/cancelled/held result. No raw invitation/resume token, password, password hash/fingerprint or session bearer material is stored or logged. Resume secrets, if needed, use a separate bounded capability whose digest and lifetime are stored; an operation UUID is not a credential.

Enforce one reservation per invitation generation and one live operation per invitation, even with different request keys. An already-consumed generation can never gain another provider attempt by supplying a new key. Require idempotency-key uniqueness in the accepted caller/purpose namespace and immutable request semantics excluding passwords; key reuse with different invitation, principal or purpose fails. A retry may recover the same result only with the same authenticated principal or bound resume capability. Possession of the old invitation token after claim is not sufficient to resume, authorize a new attempt or read identity/operation details.

Represent institution and platform invitation references with actual foreign keys and an exactly-one-kind constraint, or separate operation tables with equivalent invariants; a free-form kind plus unconstrained UUID is insufficient. Freeze the operation's binding after reservation and prohibit caller-written readiness/result fields. Recovery progress may advance through guarded transitions, but cannot change the reserved recipient, tenant, role, generation or command purpose. If linked to a membership request, retain its immutable applicant/request provenance rather than accepting a new request ID at finalize.

The existing table only permits invited/accepted/cancelled/expired [checks:51–89](../../../supabase/migrations/20261001020000_phase_7_14_super_admin_university_admin_lifecycle.sql#L51). Its [transition guard:131](../../../supabase/migrations/20261001030000_phase_7_15_invitation_delivery_email_verification.sql#L131) treats every state except invited as terminal and only permits rotation while invited. Therefore accepting cannot be introduced by a backend change alone. A future forward migration must revise compatible checks/guards, preserving immutable tenant/role/email/issuer binding and terminal token irreversibility. Accepted should mean identity preparation, authorized role completion and required audit committed, not merely reservation won.

Alternative: keep existing lifecycle states and use a reservation ledger with every writer consulting it under the same invitation lock. This is viable only if **all** table/RPC writers are constrained: existing `.eq(status, invited)` cancel/claim and rotate can otherwise act during reservation. Alternative early accepted marking also obscures acceptance success and complicates new-account binding. Neither is the preferred default. Generation is useful explicit evidence but not a replacement for digest comparison; the presented token does not need to encode generation. Backend hashes the actual bounded token and obtains the current generation; the DB compares both under lock. Existing pending tokens can be assigned an initial generation through an approved forward backfill without reissuing links or pretending to reconstruct earlier generations.

### Begin-reservation transaction

1. Backend validates/rate-limits the request. For existing-account mode, it verifies JWT subject → canonical active application/Auth identity and stored recipient match before any mutation. For new-account mode, the current invitation is the bounded capability; client role, tenant, issuer and target identity fields are rejected. Public inspection remains non-authoritative.
2. Begin executes only through the accepted trusted backend entry. Check authentic service context and explicit effective access, reject null/missing mandatory context, lock the invitation, then re-read the row and validate current status, expected generation and **presented digest**, immutable binding, role allowlist and active tenant/required issuing-authority policy. This re-read, not the earlier token lookup, determines eligibility.
3. Evaluate expiry using DB wall-clock time **after obtaining locks**, with strict `expires_at > decision_time`. For a lock wait crossing expiry, refuse. `now()` is transaction-start time; `clock_timestamp()` provides current time. Capture one decision timestamp rather than compare against a backend precomputed time. Record that ordering rule explicitly: eligibility at the locked decision, not an impossible guarantee that commit precedes every real-time expiry. [PostgreSQL date/time semantics](https://www.postgresql.org/docs/17/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)
4. Atomically create the unique operation, change invited → accepting, freeze digest/generation/binding and append a reservation event. No application user is required yet for a new account; do not invent a human actor FK for a pre-identity operation. DB failure, including mandatory event failure, rolls back all these changes. Return only bounded operation state/resume material to the trusted service; do not echo stored digest or provider credentials.
5. Commit before invoking the identity provider. One request wins; others are denied or return an authorized same-operation status. Unique constraints and locking enforce this independently of process-local locks. An unknown begin response is resolved by operation lookup with its original key; **never** perform provider I/O merely because the client timed out. No DB transaction is held open over provider I/O.

Row locks serialize conflicting writers; under Read Committed a waiting row lock sees the updated row, whereas higher isolation can require transaction retry. All checks must follow the acquired lock and retries must retain operation identity. [PostgreSQL locking](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS), [isolation](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED). These semantics do not prove correctness of unwritten commands.

### Rotation, cancellation, expiry and interleavings

| Ordering / policy proposal | Required state and outcome |
| --- | --- |
| Rotation commits before begin | Under invitation lock, rotate only invited/unexpired, compare expected generation, update digest+generation+expiry and atomically supersede pending outbox/add successor job. Begin with old digest/generation fails with no operation, identity effect or role/audit-success event. Retain current refusal during active outbox provider I/O unless an independently accepted replacement policy exists. |
| Begin commits before rotation | Invitation is accepting; rotate is denied, with no new digest/job. The claimed generation remains consumed. Timestamp concurrency tokens are auxiliary; they do not authorize claim. |
| Cancel commits before begin | Authorized cancel sets cancelled and appends its event in one transaction; begin fails. Expiry likewise prevents begin whether or not sweep ran. Cancellation must not trust a resource tenant or actor supplied by an unverified caller. |
| Cancel arrives after begin but before finalize | Recommended owner-review policy: record a durable cancellation request under the same invitation/operation lock; block **new role finalization**. If no provider call has started, terminalize cancelled directly. If an external call is started/uncertain, hold operation for reconciliation; do not claim that password/created-identity effects were undone. A definitive resolved cancellation may set accepting → cancelled, retaining consumed generation. |
| Finalize commits before cancel | Acceptance is terminal; cancellation cannot undo it. Return already completed/conflict; a later role revocation is a separate authenticated/audited command. Never report cancellation as credential rollback. |
| Token expiry after successful begin | Proposed policy: begin consumes before expiry and has a separate bounded completion deadline; finalization may occur after token expiry only within that deadline and with all current checks. Deadline length is an owner decision. Original token expiry alone must not reopen or supersede an accepting operation. Expiry sweep handles invited only; overdue accepting becomes held/cancellation-requested through the recovery contract. |
| Duplicate/concurrent accepts | Different keys cannot win another operation/provider start. Same key/principal returns the existing status/result without repeating a completed step. Losing request cannot supply a replacement password to the winner. |
| Crash/lease expiry during provider I/O | Do not treat a lease expiry as evidence that the external call did not occur. Hold/unknown; reconcile before assigning another executor. A DB fencing version cannot stop an old HTTP call at a provider that ignores that version. No automatic return to invited, token reactivation or blind provider retry. |

Cancellation/deadline policy is proposed, not accepted. A simpler claim-wins cancellation policy is another option, but the UI/API must then explicitly say cancellation cannot stop an already-claimed acceptance. Owners must select one and test both orderings. Existing direct cancel/sweep consumers must be routed/restricted accordingly. Lock order across invitation/request, operation, tenant/authority/users, role rows, outbox and audit must be reviewed across **all** commands; use deterministic ordering for multiple actors/resources. Handle deadlock/serialization retries as same-operation retries, never as permission to repeat an uncertain provider step.

The existing unique pending-email index covers invited only [outbox migration:135](../../../supabase/migrations/20261002000000_phase_7_17_email_outbox_worker.sql#L135). Its successor must cover unresolved accepting operations or provide equivalent uniqueness. Otherwise issuing a second invitation can bypass single-use recovery semantics. No destructive deduplication is assumed; existing duplicates/conflicts require preflight and owner disposition. If invitation-driven credential changes are retained, serialization must also cover **canonical account across invitation kinds/tenants**, not just one invitation. Independent password-reset writers require a declared priority/coordination policy; a DB lease alone cannot fence the provider.

## 4. P02: identity preparation, password sequencing and recovery

### Preferred existing-account flow

Accept a current token plus a verified session for the same canonical identity. Match stored normalized recipient to the trusted Auth/application mapping; reject inactive accounts, missing/ambiguous mappings, changed email, wrong session and unverified ownership according to the approved email policy. Never select another existing identity solely by an untrusted request email. Reserve, then finalize membership without modifying password, profile names or provider email. If access is lost, the user completes the separate recovery flow and then authenticates; invitation acceptance does not itself reset credentials. An accepted membership response grants no provider session automatically.

This is a product/API change: [current request requires password:104](../../../backend/app/schemas/admin_invitations.py#L104); [frontend accept:130](../../../frontend/src/services/adminInvitationApi.ts#L130) currently posts password without this new authenticated contract. Keep a separate new-account path using a chosen password; current admin-invitation rejection of existing accounts [service:702](../../../backend/app/services/platform_admin_invitations.py#L702) remains unless owners explicitly extend it. Do not silently ignore an old password field and return apparent credential-change success. Version/deprecate the existing staff/faculty behavior with an explicit UI transition and consumer acknowledgment.

### New-account preparation after reservation

Once begin commit is known, record provider-step intent before creating Auth identity. Request-scoped passwords go only to the provider; no background job stores/replays them. Use documented provider idempotency/correlation only if supported for the actual version. On success, record canonical Auth ID and bind the application user through a reviewed unique Auth-ID/email mapping, preserving the current registration semantics. [Auth account creation:286](../../../backend/app/services/student_registration.py#L286), [public user creation:345](../../../backend/app/services/student_registration.py#L345) are separate operations today. Concurrent signup may create an existing identity after the initial check: do not reset it, delete it or treat duplicate email as proof that this operation owns it. Require authenticated reconciliation or terminate/hold safely.

No invitation role is issued until identity preparation and operation evidence are ready. A prepared account may still have whatever baseline sign-in behavior the provider/registration assigns; this design does not promise that creating a user itself grants no unrelated default privileges. Review those grants before accepting the preparation contract. If a public-user/role/audit step later fails, retain operation ownership evidence and reconcile. Automatic deletion of an existing/shared account is forbidden; even an operation-created identity may have concurrent sessions/data/FK references, so cleanup requires separately accepted proof and an audited decision. Preserve restrictive audit references and history rather than deleting them to make compensation succeed.

### Compatibility option: invitation-driven existing password update

This option requires explicit security/product approval that a **current** invitation is a credential-changing capability for an existing identity. It is less robust than the preferred authenticated membership flow and must not be adopted by default to preserve a UI field. After durable reservation and canonical identity binding, authorize one provider step through operation/account coordination. Check cancellation/deadline before admitting the step; do not hold a DB transaction across it. Provider failures have three materially different outcomes:

| Provider/DB outcome after reservation | DB, identity-provider and recovery contract |
| --- | --- |
| Definitive rejection with documented no mutation | No role, accepting operation failed/held with explicit failure event; provider credentials unchanged according to that documented response. Resume only with bound principal/capability and a reviewed new attempt; obtain password anew. If cancelled, terminalize cancelled. No old invitation reuse. |
| Successful password change, but recording/finalization fails | Credentials have changed; operation remains accepting/held, no newly finalized role. Preserve provider correlation and reconcile the same operation. Do not restore/log an old password, reissue the old token, delete identity or pretend overall rollback. Successful required audit/finalization is still needed. |
| Timeout, reset connection, ambiguous 5xx, or crash after request | Password state is **unknown**, not unchanged. Never replay on lease expiry, accept a different password through another request or conclude that a profile read reveals password state. Require provider-supported outcome evidence or fresh verified user recovery/authentication under an explicitly accepted resolution contract. Record uncertainty and keep role finalization blocked. |
| Cancellation/revocation while call is in flight | External mutation may finish after cancellation. No new role finalization once cancellation wins its locked DB decision; record resolved or unknown provider effect separately. Notify/recover through authenticated, approved channels later; no messaging was performed here. |

[Supabase Python admin update documentation](https://supabase.com/docs/reference/python/auth-admin-updateuserbyid) describes server-side password/email-confirm operations. It supplies no guarantee here of cross-system atomicity, password readback or exactly-once mutation. Provider/SDK versions, timeout retry behavior, audit/event correlation, session invalidation and documented idempotency must be evidenced. Until they are, the compatible password-coupled path is **not implementation-ready**. User recovery can restore control but does not retroactively prove whether the timed-out attempt changed credentials.

Recovery is a durable workflow with a responsible owner, bounded retry policy, authenticated status/resume endpoints and an operator queue for unknown outcomes. Record transition events and provenance; never convert unknown to success to clear a queue. If a DB response to finalize is lost, read committed operation result before retrying; an accepted result returns the same outcome with no extra role or success audit. If success cannot be established, expose pending/recovery-required, not acceptance success.

## 7. P05: audit, delivery and recoverable outcomes

Reservation/pre-identity events need their own accepted append-only representation: actor modality (verified account, token capability, system/operator), subject, issuer/approver, operation ID, generation reference, transition, timestamp and redacted outcome. Proposed finalize transaction includes role/main audit, accepted invitation, operation result and required institution acceptance/verification event (or a mandatory durable dispatch record whose downstream dedupe/retention contract is accepted). Main audit failure rolls back role and acceptance but **cannot** roll back an earlier provider mutation. Distinguish role-change audit (one per actual change) from acceptance event (one per completed operation); existing identical role needs acceptance evidence even without another role-change event. Retry a separate outcome event/update only after the failed state is established; if that also fails, durable prior reservation/provider-intent evidence plus redacted operational error is the limit. Do not claim complete audit or successful recovery when DB logging is unavailable. A durable dispatcher cannot guarantee exactly-once external delivery; use stable IDs/idempotent consumers and show both DB enqueue and downstream outcome evidence.

Pending invitation-email jobs are cancelled/token-cleared when leaving invited [terminal-email trigger:115](../../../supabase/migrations/20261002000000_phase_7_17_email_outbox_worker.sql#L115); current resolver allows invited/current token only [latest resolver:78](../../../supabase/migrations/20261004000000_phase_7_23_staff_faculty_onboarding_roster.sql#L78).
