# ADR-ENROLLMENT-003: Identity, admission episodes and academic history

Date: 2026-10-11 (Asia/Calcutta). Status: final recommendation for review; adoption and execution require approval. This supersedes the recovered ADR-002 proposal as a design recommendation, without modifying it. No database was connected and no SQL was executed.

1. Preserve `students.student_id` and its unique link to `public.users.id`. Readmission, transfer and program change never create a second identity. Keep account status (`users.status`), registration approval (`students.approval_status`) and identity archival (`students.is_active`) separate from admission approval and academic lifecycle. Supabase Auth remains the credential authority.
2. Adopt all four proposed tables because each addresses a verified dependency: identifiers must survive repeated admissions; episodes distinguish immutable institution/program ownership; placements distinguish promotion and repeated attempts; events explain decisions, concurrency and corrections. Notifications and `admin_audit_log` cannot substitute for an enrollment ledger. Do not add a new class table or universal subject-membership table.
3. An enrollment represents one institution/program admission episode. Student and institution are immutable. Program may be completed once from NULL while an application is pending and has no placement; changing a known program creates a successor episode. Readmission creates a successor after an earlier terminal episode. Transfers use distinct institutions and require both institutions' decisions. Program changes use distinct programs in the same institution. Predecessors must belong to the same student; edges must be chronological and cannot form cycles.
4. Recommend at most one approved `active` or `on_leave` episode per identity globally. Pending applications can coexist. The SQL draft includes this recommendation explicitly. Dual enrollment requires a separately reviewed selection, interval, permission and UI design; do not remove the index alone to enable it.
5. Admission approval is `pending/approved/rejected`. Lifecycle is `pending_admission/active/on_leave/graduated/withdrawn/transferred_out/cancelled/legacy_unresolved`. `legacy_unresolved` describes a quarantined snapshot, never an academic entitlement. Rejection yields rejected + cancelled; cancellation may retain pending or approved admission approval. An approval does not activate an episode.
6. Activation requires an approved registration, an active account/profile/institution, verified mapping, an evidence-backed admission date, a verified institution-issued student number, and a verified initial placement. Also require at least one verified register or university roll identifier. This is a conservative default; institutions must confirm their mandatory identifier rules. Date-effective commands execute on their effective day; future transitions remain applications/planned decisions until an explicit activation command. The draft uses IST for this boundary.
7. Identifier ownership is unique by institution, kind and ASCII-whitespace-trimmed value with deterministic `C` collation. Preserve case, punctuation, Unicode and leading zeros. Email remains account/profile contact, not an institutional academic number. University roll numbers remain institution-scoped, matching existing schema; a university-wide namespace needs a separate authority model. Reuse by the same person references the existing identifier; never recycle a verified number to another person by default. Self-reported claims belong in application provenance until verified, rather than creating permanent ownership reservations.
8. Placements use evidenced half-open intervals `[starts_on, ends_on)`, year/semester ancestry and an attempt number. No overlap inside an episode, including under concurrent writes. Attempt means a repeated curriculum semester ordinal, even when the concrete semester UUID/year changes. Subject-specific `sections` remain attached to course offerings; placement is not subject enrollment. A supplementary assessment belongs to its original attempt and does not create a placement simply because its exam date is later.
9. Events are append-only, sequenced per enrollment under a row lock, and capture operation envelope, actor, reason, source/evidence, before/after state, effective date and correction references. One logical operation can produce one event per affected enrollment; `(operation_id,enrollment_id)` is unique. All events in an operation must carry the same canonical request. State, placement, events and mandatory audit writes commit together. Return the original event response on an identical retry, including after later state changes; reject a changed payload or actor before returning it. Recheck authorization on retries.
10. Terminal episodes do not reopen. Resumption from leave uses the same episode and a new placement interval; semester attempt need not increase merely because of leave. A new admission after graduation/withdrawal is readmission. Administrative correction appends a correction event. Changes affecting ownership, published marks or historical dates need a reviewed correction transaction; the draft annotation command cannot silently rewrite them.
11. Historical records retain their original student, institution, program, academic period, publication state and primary keys. Selected current context is never the owner of all past records. Freeze publication facts independently of present roster/registration activity. Historical student reads require own identity, approved original admission, active account, and explicit historical-access policy; they do not grant current resources, notices, upcoming assessments or faculty privileges.
12. Legacy registration timestamps are not admission evidence. No fabricated dates, default current semester, or guessed meaning of `inactive`. Missing/ambiguous records remain in quarantine with source evidence and a resolution queue. Retain legacy snapshots in events; create no placement where period/date evidence is missing.
13. Backend-only access is the default. Clients receive no direct grants on new tables/RPCs. Backend reads use SELECT; mutation uses narrowly authorized SECURITY DEFINER routines. Reuse the existing institution-admin assertion and master ancestry guards. New RPCs are admin-only initially; existing staff approval permissions do not silently become enrollment lifecycle authority.
14. Adopt by additive, gated stages. Do not update legacy membership columns to simulate transfers while current guards remain installed. The review DDL has an unconditional execution stop and ends with ROLLBACK; a later approved migration must deliberately remove the stop and choose a commit boundary. It is a candidate core schema, not a compatibility cutover.

Institutional confirmations: single operational enrollment; case/namespace and mandatory identifiers; readmission number retention; attempt counting across curricula; leave limits; transfer consent/approval expiry; historical access after institution archival; legitimate backdated corrections; retention/anonymization. Safe defaults and blockers are enumerated in [the schema review](STUDENT_ENROLLMENT_SCHEMA_FINAL_REVIEW.md).

Consequences: four tables and coordinated identity-resolution, academic-record, roster, trigger, API and cache changes. SQL can protect new core objects, but existing publication and record-ownership behavior must be replaced before operational cutover. The recommendation is **NO-GO for disposable execution now**, with a precise approval and preparation path in [the summary](REVIEW_SUMMARY.md).
