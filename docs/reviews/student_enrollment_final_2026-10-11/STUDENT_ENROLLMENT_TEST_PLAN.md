# Student enrollment synthetic test plan

2026-10-11 (Asia/Calcutta). **Prepared, not executed.** No database test, application test, Docker command or SQL statement ran during this review. Fixtures in [synthetic fixtures](synthetic_fixtures.json) are specification data, not an SQL seed or executable test loader.

## Fixture contract

All people, identifiers and institutions are invented. Fixed UUIDs use distinct ranges for institutions, departments/programs, users/students and academic masters. `D` means the authorized validation run's actual date in Asia/Kolkata; offsets are resolved by the future fixture loader. Scenarios are isolated and reset in separate run-owned disposable databases or transactions. Do not manufacture production history from these examples.

Master data defines A/B institutions, A1/A2/B1 programs through their departments, local years, several concrete semesters and subject offerings/sections. `A_S1` and `A_REPEAT_S1` have the same curricular ordinal but different UUIDs/years. Their dates must satisfy the existing active-year no-overlap exclusion. The loader must set old years noncurrent/inactive as appropriate; archived masters remain valid historical references. Real current semester dates include D; past periods end before D. Section ownership is subject-specific.

`S1` and `S2` have distinct `users.id` and Auth links. `ADMIN_A`, `ADMIN_B` have scoped active admin role and granular student permissions; `FACULTY_A` has only approved section/test/attendance permissions. An application student actor cannot become a database service role. Owner-only historical fixture construction must insert valid creation/transition events for each version and audit expected changes; it is not the production importer. Restrictive FK and deferred event guards remain enabled. It may construct an evidenced historical starting state for a single isolated scenario, so a same-day current RPC can test resumption/readmission/promotion. Never change system clock or permit a production `allow_backdate`/test-bypass argument.

The future loader must insert existing baseline-required columns through the verified full-chain schema and existing sanctioned workflows, including program curriculum/course offering and section requirements. The JSON uses references, not incomplete purported database rows. Each concrete fixture insertion plan must be reviewed against master and workflow guards before execution.
