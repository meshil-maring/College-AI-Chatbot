# Student enrollment prerequisite security containment review

Prepared 2026-10-11, Asia/Calcutta. **Source-only review; PostgreSQL validation NOT RUN.** This review recommends a separately approved containment candidate. It does not install a fix, authorize SQL execution, or establish any current local or remote effective privilege.

The minimum prerequisite work is to contain audit mutation privileges, remove the six documented sensitive RPC client exposures by exact signature, stop unsafe future routine defaults, and explicitly deny client table/column access to the enrollment authority and academic dependencies. Preserve backend workflow grants and all integrity/authorization triggers. Changes to function bodies, maintenance ledgers, deployment creators, or inherited role access need the additional dependency decisions below. No production migration was created.

Read in conjunction with [SQL_REPAIR_REVIEW.md](SQL_REPAIR_REVIEW.md), [REVIEW_SUMMARY.md](REVIEW_SUMMARY.md), [STUDENT_ENROLLMENT_SECURITY_REVIEW.md](STUDENT_ENROLLMENT_SECURITY_REVIEW.md), the unchanged [enrollment SQL](student_enrollment_schema_review_draft.sql), and the [ordered change plan](SECURITY_CONTAINMENT_CHANGE_PLAN.md). This report supplements their security prerequisites; it does not supersede the SQL repair contract or institutional decisions.

## Evidence boundaries and method

All 39 migration files were inventoried in filename order. Relevant declarations, grants, revocations, policies, defaults, triggers and function replacements were inspected alongside backend consumers and frontend access patterns. Source ordering includes future-named files through `20261016010000`; it is not evidence those versions have been applied. Historical M1/security reports are background only. No historical catalog snapshot was promoted to a current finding. No external services, database, Docker, SQL parser or application/harness tests were used.

Confirmed source defects below mean explicit unsafe grants/defaults or missing source containment. An effective exploit additionally depends on actual applied bytes, creating role, bootstrap/global/schema defaults, ownership, PUBLIC/direct/inherited/settable grants, column ACLs, request claims, RLS bypass and exposed schemas. In particular, **the reconstructed baseline grants authority tables to service_role, not explicitly to anon/authenticated.** Absence of a client revoke is not proof of current client CRUD access.

[Static results](SECURITY_CONTAINMENT_STATIC_RESULTS.json) retain migration hashes, statement/line inventories, function declaration history and overloads, renames/drops, explicit ACL events, backend literal RPC call sites and dynamic-call gaps. The [rerunnable checker](verify_security_containment_static.py) performs bounded lexical checks; it is neither a PostgreSQL parser nor an effective ACL evaluator. Automated findings and manual security conclusions are separate.

## SC-01 — High: audit ACL permits destructive operations beyond the guard

**Affected:** `public.admin_audit_log`, its column ACLs, `phase81_prevent_audit_mutation()`, and `phase81_admin_audit_append_only`.

**Exact source:** [Admin-1, 479–509](../../../supabase/migrations/20260909000000_phase_admin_1_admin_student_schema.sql#L479) defines UUID/default audit ID, non-null public-user actor, action/status constraints and actor FK `ON DELETE RESTRICT`; [566–575](../../../supabase/migrations/20260909000000_phase_admin_1_admin_student_schema.sql#L566) grants ALL on the audit table to service_role. [Baseline, 1182–1183](../../../supabase/migrations/20250717000000_reconstructed_pre_phase_3_6_baseline.sql#L1182) grants future public tables ALL to postgres/service_role. [Phase 8.1, 40–45](../../../supabase/migrations/20261006000000_phase_8_1_scoped_rbac_and_faculty_assignments.sql#L40) adds institution scope/FK; [123](../../../supabase/migrations/20261006000000_phase_8_1_scoped_rbac_and_faculty_assignments.sql#L123) grants INSERT, without subtracting existing ALL; [505–519](../../../supabase/migrations/20261006000000_phase_8_1_scoped_rbac_and_faculty_assignments.sql#L505) installs the rejecting BEFORE UPDATE OR DELETE row trigger. [Phase 10, 200](../../../supabase/migrations/20261010000000_phase_10_faculty_attendance_management.sql#L200) again grants service-role SELECT/INSERT/UPDATE/DELETE on ALL public tables.

**Source-supported behavior:** service_role is granted UPDATE, DELETE and TRUNCATE at the ACL level. With the documented row trigger enabled, UPDATE/DELETE affecting audit rows raise `insufficient_privilege`; zero-row operations do not fire a row trigger. TRUNCATE does not fire that UPDATE/DELETE trigger and is outside RLS row protection. No source migration adds an audit TRUNCATE guard, enables RLS on admin_audit_log, defines an audit RLS policy, or explicitly revokes its service-role destructive privileges. Table privilege and trigger protection are different layers. Whether an actual attempted truncation succeeds also depends on catalog constraints, roles and trigger state; no attempt was made.

**Minimum proposal:** in a separate forward transaction after the full existing chain, preserve SELECT/INSERT for service_role and owner/nested audit writes; explicitly revoke service-role UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER and, for the PostgreSQL 17 target, MAINTAIN. Revoke any independently granted column UPDATE/REFERENCES, not just table privileges; remove grant options and effective client/PUBLIC table and column access. Enable RLS on admin_audit_log without client allow policies. If service-role BYPASSRLS is absent in the approved target, narrowly support its necessary SELECT/INSERT through reviewed policies, with no audit mutation policy. Keep the existing row trigger/function unchanged. Add a distinct BEFORE TRUNCATE FOR EACH STATEMENT rejecting trigger as defense in depth; preserve the existing trigger binding expected by enrollment preflight. Restrict the new trigger helper's EXECUTE to its owner, and remove client EXECUTE on the existing helper. Owner/superuser disabling guards remains a trusted maintenance boundary.

**Compatibility:** [admin_audit repository, 24–41](../../../backend/app/repositories/admin_audit.py#L24) inserts/reads, not update/delete/truncate; [list reads, 49 onward](../../../backend/app/repositories/admin_audit.py#L49) also need SELECT. Existing SQL mutation routines insert audit rows atomically as definers. Do not revoke service-role INSERT as a purported forgery fix: current trusted backend audit writers require it. Direct service-role INSERT can still supply actor/provenance; ACL containment does not authenticate the human actor. Any retention, reset or cleanup that mutates this ledger needs a separate owner-maintenance decision; none is inferred authorized.

**Regressions:** T01–T04 and T12 in the plan. **Independent approval:** yes, exact legacy audit ACL/RLS/trigger migration candidate and retention compatibility. No approval is needed or requested for this completed review.

## SC-02 — High: future function defaults recreate client exposure

**Affected:** new functions made by postgres in public; potentially other deployment creators after catalog inventory.

**Exact source:** [Baseline, 1172–1175](../../../supabase/migrations/20250717000000_reconstructed_pre_phase_3_6_baseline.sql#L1172) grants future FUNCTION ALL/EXECUTE to postgres, anon, authenticated and service_role. There is no subsequent source ALTER DEFAULT PRIVILEGES revocation. No source statement changes the initial global PUBLIC routine EXECUTE default. Source does not establish other creators' defaults or current `pg_default_acl`.

**Source-supported behavior:** on creation by the indicated role/schema, explicit anon/authenticated defaults are independent of PUBLIC; revoking PUBLIC on one routine does not remove their direct defaults. service_role also inherits routine EXECUTE by that default, including private helpers unless explicitly revoked. Existing routine ACLs survive CREATE OR REPLACE, illustrated by the resolver replacement in [Phase 7.23, 71–97](../../../supabase/migrations/20261004000000_phase_7_23_staff_faculty_onboarding_roster.sql#L71). Owner EXECUTE is a separate trusted capability.

**Minimum proposal:** remove the postgres/public explicit anon/authenticated function defaults, and revoke global PUBLIC future-function EXECUTE for that creator (a schema-specific revoke cannot subtract a global default). Adopt explicit grants for new service-only entry points; remove postgres/public automatic service_role FUNCTION EXECUTE once all future creators/workflows have an explicit grant contract. Apply corresponding global/schema changes to another creator only if later approved catalog evidence establishes it actually creates these objects. Do not change unrelated sequence/table defaults in this narrow fix; separately prevent future broad table grants. Defaults do not repair existing functions: apply SC-03 plus an explicit signature allowlist. For each new enrollment function, revoke ALL from PUBLIC/anon/authenticated/service_role immediately inside its creation transaction, then grant only the two reviewed command entry points to service_role, as the draft already proposes.

**Compatibility:** global PUBLIC default changes affect future functions across schemas made by that creator; other deployment pipelines/extensions need review before expansion. Revoking future service defaults can reveal migrations that depend on implicit helper/trigger EXECUTE at trigger creation or backend direct calls. Keep explicit service EXECUTE on existing workflows until their dependencies are traced. Do not issue REVOKE EXECUTE ON ALL FUNCTIONS or drop legacy overloads. Dropping service-role EXECUTE on an invoker trigger helper can break nested invoker calls even though an already-bound trigger is not an ordinary RPC; investigate each body/caller.

**Regressions:** T05, T07, T08, T11–T12. **Independent approval:** yes, exact creator/schema/global default scope and future migration compatibility; other creators/schema changes require their own reviewed scope.

## SC-08 — High: broad service grants defeat earlier least-privilege intent

**Exact source:** [baseline future TABLE ALL, 1182–1183](../../../supabase/migrations/20250717000000_reconstructed_pre_phase_3_6_baseline.sql#L1182), [Phase 10 schema-wide service DML, 197–200](../../../supabase/migrations/20261010000000_phase_10_faculty_attendance_management.sql#L197).
